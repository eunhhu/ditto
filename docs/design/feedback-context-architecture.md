# 피드백 노트: LLM 하네스 컨텍스트 가상 페이징 및 마이크로커널 아키텍처

> 작성일: 2026-10-05  
> 대상: Ditto Semantic Agent Microkernel 및 하네스 설계 (`docs/design/realtime-harness.md`, Context IR)

---

## 1. 문제의식: 기존 LLM 하네스의 한계

1. **에이전트 간 자유 대화(Multi-agent Chit-chat)의 비효율성**
   - 에이전트끼리 자연어로 토론하여 결론을 도출하는 방식은 턴이 거듭될수록 동조 편향(Sycophancy)과 확증편향이 심화됨.
   - 모델 자체의 추론(Reasoning) 역량이 충분한 현시점에서 다자간 만담은 막대한 토큰 낭비와 컨텍스트 오염만 초래함.
   - 멀티에이전트의 유일한 존재 이유는 **"메인 컨텍스트 보호를 위한 철저한 격리형 워커(Worker Process)"**여야 함.

2. **모놀리식 컨텍스트와 원시적 Truncate**
   - 메인 모델이 수천 줄의 원시 코드(Raw code)나 장대한 빌드/에러 로그를 직접 읽으면 Attention Dilution(주의력 분산)으로 인해 핵심 제약을 망각함.
   - 기존의 단순 Truncation(앞/뒤 일부만 남기고 자르기)은 중간의 핵심 단서나 에러를 유실시킴.
   - LLM 기반의 무차별적 요약은 느리고, 비용이 들며, 비결정론적(포맷 훼손 및 환각)임.

## 2. 핵심 설계 1: 컨텍스트 메모리 세그멘테이션 & 가상 페이징

OS의 가상 주소 공간(`Text / Data / Heap / Stack`)과 유사하게, 1M(또는 128k~200k) 컨텍스트 윈도우를 **엄격한 3~4개 세그먼트**로 분할하여 관리한다.

```
[ 전체 Context Window 예: 1M ]
┌─────────────────────────┬───────────────────────────────────────────┬───────────────────┐
│ 1. Text Segment (200k)   │ 2. Task Ledger Segment (600k)             │ 3. Working (200k) │
│ [RO / Constant Cache]   │ [Dynamic Budgeting / Task Table]          │ [Scratchpad]      │
├─────────────────────────┼───────────────────────────────────────────┼───────────────────┤
│ • 시스템 불변 룰         │ • Task A (가중치 0.4): 서브 결과 슬롯     │ • 현재 진행 턴의  │
│ • 실패 엣지케이스 족보   │ • Task B (가중치 0.2): 서브 결과 슬롯     │   즉각 맥락       │
│ • 최종 프로젝트 목적     │ • Task C (가중치 0.4): 서브 결과 슬롯     │ • 직전 3~5턴 Raw  │
│ (KV 캐시 100% 영구 히트)│ (슬롯 포화 시 가중치 기반 우선순위 Evict) │ (Tail 보호)       │
└─────────────────────────┴───────────────────────────────────────────┴───────────────────┘
```

### A. 불변 텍스트 세그먼트 (Constant Prefix)
- **구성**: 시스템 코어 지시, 최종 목적, 아키텍처 불변 제약, **실패 엣지케이스(Pitfalls / Anti-patterns) 족보**.
  - *원칙*: 성공 레퍼런스는 이미 사전학습에 풍부하므로, 현 환경 고유의 '실패 패턴' 정보가 탐색 공간을 극적으로 좁혀주는 핵심 고밀도 엔트로피임.
- **효과**: 세션 내내 1글자도 변하지 않으므로 제공사(Anthropic, OpenAI, DeepSeek 등)의 **KV 캐시(Prompt Caching)가 100% 영구 적중**. 비용 80~90% 절감 및 TTFT(첫 토큰 시간) 극소화.

### B. 태스크 원장 세그먼트 (Task Ledger)
- 서브에이전트가 완수한 단위 작업의 결과물만 정형화된 슬롯 형태로 수용.
- **예산 강제(Budget Enforcement)**: 각 태스크 슬롯마다 허용되는 최대 토큰/문자 한도를 하네스가 엄격히 제한.
- **우선순위 기반 페이징/축출 (Priority-based Eviction)**:
  - 공간 부족 시 전체를 요약하지 않고, **중요도 가중치**에 따라 완료된 하위 태스크(`status: DONE, exit: 0`)부터 최소 메타데이터로 폴딩(Paging-out).
  - 현재 크리티컬 패스에 있는 핵심 태스크는 세부 사양을 보존.

### C. 워킹 스크래치패드 (Working Window)
- 최근 3~5턴의 대화 원문(Raw)을 유지하여 자연스러운 문답과 즉각적인 도구 호출 연속성을 보장(Tail Protection).

## 3. 핵심 설계 2: 마이크로커널 Ring 격리 (메인의 Raw I/O 물리적 차단)

- **메인 에이전트 (Ring 0 / Orchestrator)**:
  - **원시 코드(Raw source code) 및 방대한 로그를 직접 읽는 것이 물리적으로 금지됨.**
  - 직통 툴 호출이 불가피할 경우, 하네스 인터셉터가 사전에 엄격한 `output_limit` 하드 캡을 강제함.
  - 메인의 임무는 오직 상태 전이, 아키텍처 판단, 서브에이전트 디스패치 및 슬롯 결과 취합.
- **서브에이전트 (Ring 3 / Userland Worker)**:
  - 수천 줄의 파일 탐색, 빌드 로그 분석, diff 검토 등 오염도가 높은 작업을 전담.
  - 작업 완료 시 계약된 엄격한 스키마(Strict JSON)의 초고밀도 요약만 메인에 반환하고 프로세스를 즉시 종료(`exit(0)`).

## 4. 핵심 설계 3: 데이터 포맷별 반응형 계약 요약 (Semantic Folding)

웹 프론트엔드의 미디어 쿼리(`@media`)처럼, 도구 출력의 데이터 크기에 따라 **LLM 없이 기계적·결정론적으로 해상도를 조절**하는 반응형 요약 인터셉터.

| 도구 / 데이터 유형 | 소규모 (Full Detail) | 중규모 (Structural Detail) | 대규모 (Topology / Index Only) |
| :--- | :--- | :--- | :--- |
| **파일 트리 (FS Explorer)** | **20개 이하**: 전체 경로, 파일 크기, 권한, 수정일 | **100개 내외**: 디렉터리 트리 + 파일명 + 대략적 용량 | **500개 이상**: 최상위 토폴로지 + 파일명 목록 + 확장자 분포 통계 |
| **Git Diff (Code Changes)** | **100줄 이하**: Unified Diff 전체 출력 | **500줄 내외**: 파일 목록 + 변경 줄 수(`+12, -4`) + 함수/클래스 시그니처 | **2,000줄 이상**: 파일별 변경 상태(`M/A/D`) 및 영향 받는 모듈 맵 |
| **에러 / 빌드 로그** | **50줄 이하**: 원문 전체 출력 | **200줄 내외**: 앞뒤 컨텍스트 + 직전 커맨드 | **대규모 덤프**: 원문 버림. 정규식/AST 기반 `Error/Panic/Traceback` 추출 (발생 파일:라인 + 에러 타입 + 빈도) |

- **장점**:
  1. LLM을 거치지 않아 지연시간 0ms, 추가 비용 0원.
  2. 결정론적 규칙이므로 포맷 파손이나 환각이 없음.
  3. 메인 컨텍스트의 신호 대 잡음비(Signal-to-Noise Ratio)를 항상 최상으로 유지.

## 5. Ditto 적용 권고사항

1. **Context IR 컴파일러 연계**:
   - `docs/specs/context-ir.md`의 컴파일 파이프라인에서 프리픽스(불변 룰/실패 패턴)의 위치를 항상 최상단에 고정하여 캐시 무효화를 방지.
2. **도구 런타임 인터셉터 (`crates/ditto-tool` or `ditto-harness`)**:
   - 도구 실행 반환 파이프라인에 포맷별 `Semantic Folder` 미들웨어를 두어, 반환 바이트 크기에 따라 적응형 해상도로 축약 후 컨텍스트에 주입.
3. **서브에이전트 러너 격리**:
   - 서브에이전트 실행 시 메모리 공간과 컨텍스트를 별도 격리하고, 상위 세션 주입 시 지정된 JSON 스키마 슬롯 크기를 넘지 못하도록 가드레일 적용.
